# รายงานสถาปัตยกรรม AUDRIX RELAY

วันที่: 2026-10-11

ไม่มี `GLOSSARY.md` และไม่มี ADR ในโปรเจกต์นี้ ชื่อโดเมนด้านล่างใช้คำที่โค้ดใช้อยู่แล้ว: capture, packet, session, playback

คำสถาปัตยกรรมใช้ตามที่กำหนด: module, interface, depth, seam, adapter, leverage, locality

ช่วง commit ที่ดู: ตั้งแต่จับเสียง WASAPI จนถึง jitter buffer (`cca0c7b` ถึง `4c8a353`) ไฟล์ที่ถูกแก้ซ้ำคือ `src/session.rs`, `src/capture.rs`, `src/ui/`, และ `RelayService.kt`

รายงานนี้ไม่เสนอ interface ใหม่ เป็นรายการปัญหาที่ควรแก้ก่อนลงมือ

## 1. ตัวส่งเสียงมีสองทาง

**ความแรง:** Strong

**ไฟล์:** `src/session.rs` (`capture_send` และ `send`), `src/capture.rs`, `src/packet.rs`

**ปัญหา:** การส่ง PCM มีสอง module ที่เรียก `read_pcm16` คนละลูป `capture_send` ก้อน 5/10 ms แล้วแบ่งแพ็กเก็ตให้ไม่เกิน 1200 ไบต์ `send` ส่งทั้งบัฟเฟอร์ WASAPI เป็นแพ็กเก็ตเดียว การแก้ก้อนเสียง เกน หรือ MTU ต้องจำว่ามีทางที่สอง เทสของ `even_split_bytes` ไม่ได้ครอบคลุมทาง `send` เลย

**ทางแก้:** ให้เหลือทางส่งทางเดียว ทางที่ผู้ใช้เปิดหน้าต่างและทางเช็ค localhost เรียกทางนั้น ทั้งคู่ได้ก้อนเท่ากันและการจำกัดเพดาน 16 บิต

**ประโยชน์:** locality อยู่ที่ลูปส่งลูปเดียว leverage คือหน้าต่างกับคำสั่ง `send` ได้พฤติกรรมเดียวกัน เทสยิงที่ทางส่งนั้นแทนการเทสแค่ตัวหารแพ็กเก็ต

**ก่อน:** หน้าต่างมีคิวและตัวแบ่งก้อน คำสั่ง `send` ไม่มี

**หลัง:** ทั้งสองเรียก module ส่งเดียวกัน ต่างกันแค่ปลายทางกับจำนวนแพ็กเก็ต

## 2. หน้าจอกับจุดคลิกคนละที่

**ความแรง:** Strong

**ไฟล์:** `src/ui/screens.rs`, `src/ui/mod.rs`, `src/ui/slider.rs`

**ปัญหา:** ปุ่ม Install, EN/TH, 5 ms/10 ms, และสไลเดอร์ถูกวาดที่พิกัดหนึ่ง แล้วตรวจคลิกที่พิกัดอีกชุดใน `on_click` เลื่อนปุ่มแล้วลืมแก้ฝั่งคลิกคือบั๊กเงียบ module หน้าจอจึงตื้น: interface ของการวาดกับการคลิกใหญ่พอ ๆ กับตัววาด

**ทางแก้:** ให้แต่ละหน้าเป็นเจ้าของทั้งการวาดและการตอบคลิก คนเรียกส่งเมาส์เข้าไปได้ผลลัพธ์ว่าผู้ใช้เลือกอะไร ไม่ส่งพิกัดกลับออกมาให้เดา

**ประโยชน์:** locality ของเลย์เอาต์อยู่ไฟล์เดียว leverage คือเพิ่มปุ่มแล้วเทสการคลิกได้โดยไม่เปิดหน้าต่าง Win32

**ก่อน:** `screens.rs` วาด `mod.rs` คลิก

**หลัง:** หน้าหนึ่งไฟล์รับทั้งวาดและคลิก

## 3. RelayService รู้มากเกินเรื่องเสียง

**ความแรง:** Strong

**ไฟล์:** `android/.../RelayService.kt`, `JitterBuffer.kt`, `PlaybackTrack.kt`

**ปัญหา:** การเล่นเสียงที่เพิ่งย้ายมาเป็น jitter buffer กับ playback track ลึกอยู่แล้ว แต่ `RelayService` ยังรู้ว่าต้องสร้างบัฟเฟอร์เมื่อไร ส่งก้อนไบต์เข้าไป วน `pop` และถอยเมื่อเขียนไม่สำเร็จ พร้อมกับค้นหา PC, ล็อก Wi-Fi, และเชื่อมใหม่ บั๊กเสียงต้องอ่านทั้งไฟล์บริการ ลบ `JitterBuffer` ออกแล้วความซับซ้อนไม่หาย มันไปกองในลูปของบริการ นั่นคือ module ตื้นที่ห่อของลึก

**ทางแก้:** ให้ลูปเล่นอยู่หลัง module เล่นเสียง คนเรียกรู้แค่ว่ามีแพ็กเก็ตเข้า และสั่งหยุด บริการเหลือเรื่องเชื่อมต่อ

**ประโยชน์:** locality ของอาการลำโพงขาดหรือแทร็กตายอยู่ที่ module เล่น leverage คือแก้บัฟเฟอร์ครั้งเดียวโดยไม่แตะการค้นหา PC เทสได้ผ่านก้อน PCM ไม่ต้องเปิดซ็อกเก็ต

**ก่อน:** บริการเรียก jitter buffer และ playback track เอง

**หลัง:** บริการส่งแพ็กเก็ตเข้า module เล่น แล้วรับสถานะกลับ

## 4. สัญญาแพ็กเก็ตถูกเขียนสองที่

**ความแรง:** Worth exploring

**ไฟล์:** `src/packet.rs`, `android/.../Packet.kt`, เทสทั้งสองฝั่ง, `README.md`

**ปัญหา:** หัว `sequence`, `sample_rate`, `channels` และคำว่า `FIND` / `HERE` / `PING` / `AXDR` อยู่ใน Rust และ Kotlin คนละชุด เพิ่มฟิลด์แล้วเทสฝั่งหนึ่งยังเขียวได้ ไม่มี seam ร่วม มี adapter สองตัวของเลย์เอาต์เดียวกันโดยไม่มีตัวที่สาม จึงยังไม่คุ้มที่จะสร้างชั้นแปลงกลาง

**ทางแก้:** เก็บเวกเตอร์ไบต์ชุดเดียวกันไว้ที่เดียว แล้วให้เทสทั้งสองภาษาอ่านชุดนั้น ยังไม่ต้องรวมโค้ดข้ามภาษา

**ประโยชน์:** locality ของสัญญาอยู่ที่เวกเตอร์เทส leverage คือแก้เลย์เอาต์แล้วทั้งสองฝั่งแดงพร้อมกัน

**ก่อน:** แต่ละภาษาประกอบแพ็กเก็ตในเทสเอง

**หลัง:** เทสทั้งคู่โหลดไบต์ชุดเดียวกัน

## 5. ข้อความสองภาษาซ้ำแบบตื้น

**ความแรง:** Speculative

**ไฟล์:** `src/ui/screens.rs`, `src/ui/tray.rs`, `android/.../Copy.kt`

**ปัญหา:** ประโยค EN/TH ถูกเขียนใกล้จุดที่วาด แก้คำต้องไล่หลายไฟล์ แต่ตารางสตริงอย่างเดียวเป็น module ตื้น การลบมันแค่ย้ายสตริงไปอีกไฟล์ ไม่ได้รวมพฤติกรรม

**ทางแก้:** ยังไม่แยก จนกว่าจะมีจุดที่สามที่ใช้ประโยคชุดเดียวกัน ตอนนี้ให้คำที่ผู้ใช้เห็นอยู่ใกล้ปุ่มของหน้านั้น

**ประโยชน์:** ยังไม่มี leverage พอ

## สิ่งที่ไม่ใช่ปัญหาสถาปัตยกรรม

การจอง `Vec` ทุกก้อนเสียงเป็นรายละเอียดข้างในตัวส่ง ยังไม่แยก module เอกสาร `dosc/phases.md` เก่ากว่าโค้ดเรื่อง jitter buffer กับถาดไอคอน ควรแก้ข้อความเมื่อแตะไฟล์นั้น ไม่ใช่งานสถาปัตยกรรม

## ข้อแรกที่ควรทำ

ทำข้อ 1 ก่อน การส่งเสียงคือจุดที่ถูกแก้บ่อยที่สุด และตอนนี้พฤติกรรมจริงของผู้ใช้อยู่คนละทางกับคำสั่งที่ใช้เทส แก้ก้อนหรือ MTU ครั้งหน้ามีโอกาสพลาดทาง `send` ข้อ 2 ทำต่อได้ทันทีเพราะเป็นบั๊กเลย์เอาต์ที่เกิดซ้ำทุกครั้งที่ขยับปุ่ม ข้อ 3 คุ้มหลังเสียงนิ่ง เพราะบริการกำลังโตทุกครั้งที่แก้การเล่น
