# เฟสงาน AUDRIX RELAY

ที่มาของการตัดสินใจ: [pc-audio-plan.md](pc-audio-plan.md)

เฟสจบแล้วให้เปลี่ยนสถานะเป็น `done` แล้วเติมวันกับหลักฐานหนึ่งบรรทัด (คำสั่งที่รัน หรือ commit). อย่าย้ายเฟสไปไฟล์อื่น.

สถานะมีสามคำ: `todo`, `blocked`, `done`.

ตอนเขียนไฟล์นี้ยังไม่มีโค้ดจับเสียง จึงไม่มีเฟสที่เป็น `done`.

## 0. ตรวจ APK

- สถานะ: `blocked`
- เสร็จเมื่อ: —
- หลักฐาน: —
- ขาด: ไฟล์ APK หรือชื่อแพ็กเกจ Android

เมื่อมีของแล้ว:

1. เก็บสำเนา APK
2. เปิดด้วย JADX
3. ดูด้วย adb ตอนแอปรับเสียง
4. จด protocol, port, codec, sample rate และวิธีเริ่มเล่น

ห้ามล็อกตัวส่งจากเดา. อย่าตัดสิน codec จากดักแพ็กเก็ตอย่างเดียว.

## 1. จับเสียงบน Windows

- สถานะ: `todo`
- เสร็จเมื่อ: —
- หลักฐาน: —

โปรแกรม Rust ตัวเดียว จับ WASAPI loopback แล้วพิมพ์ sample rate, channels และ buffer จากอุปกรณ์จริงบน Windows 11.

ยังไม่ส่งเน็ต. ยังไม่มี GUI. ยังไม่แยกหลาย crate.

## 2. ส่ง PCM16 ในเครื่องเดียวกัน

- สถานะ: `todo`
- เสร็จเมื่อ: —
- หลักฐาน: —

ผู้ส่งส่งเฟรม PCM16 ทาง UDP พร้อม sequence number. ผู้รับบนเครื่องเดียวกันนับแพ็กเก็ตที่หาย.

เสร็จเมื่อเสียงที่จับได้เดินทางครบรอบนี้โดยยังไม่แตะมือถือ. ตัวรับนี้ทิ้งได้เมื่อเฟส 3 รู้โปรโตคอลของ APK.

## 3. ส่งให้ตรง APK

- สถานะ: `blocked`
- เสร็จเมื่อ: —
- หลักฐาน: —
- ขาด: ผลจากเฟส 0

เสร็จเมื่อแอป Android ที่มีอยู่เล่นเสียงจากเครื่องส่งได้ใน LAN โดยไม่มีอินเทอร์เน็ต.

เกณฑ์ที่นับในเฟสนี้: จับเสียงต่อเนื่อง 30 นาที, Android เล่นต่อเมื่อปิดหน้าจอ, ใช้ได้โดยไม่ส่งออก cloud.

## 4. วัดและบีบอัด

- สถานะ: `todo`
- เสร็จเมื่อ: —
- หลักฐาน: —
- เริ่มได้เมื่อเฟส 3 เป็น `done`

ใส่ Opus, jitter buffer และเชื่อมใหม่เมื่อหลุด. จด CPU, RAM, latency และ packet loss ของ PCM16 เทียบกับ Opus จาก release build.

เป้า latency ของรุ่นแรกคือต่ำกว่า 100 ms. ยังไม่ลดไป 30–50 ms ในเฟสนี้. ทดสอบ Wi-Fi ที่มีสัญญาณรบกวนอยู่ในเฟสนี้.

- เสร็จเมื่อ: —
